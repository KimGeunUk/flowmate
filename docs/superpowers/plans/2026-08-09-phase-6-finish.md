## ★ 이 Phase의 성격이 다르다 — 되돌릴 수 없는 작업이 있다

앞의 다섯 Phase는 전부 되돌릴 수 있었다. 테스트가 깨지면 고치고, 커밋이 틀리면 다시 하면 됐다.

**public 전환은 다르다.** 한 번 공개되면 그 시점의 전체 커밋 이력이 영구히 노출된다. 나중에 커밋을 되돌리거나 저장소를 다시 private 으로 바꿔도, 그 사이에 클론·포크·크롤링된 것은 회수할 수 없다.

그래서 Task 6(비밀값 재검)이 이 계획서에서 가장 중요하고, **Task 7(public 전환)은 사용자가 직접 눌러야 한다.** 내가 대신 하지 않는다.

## 이 계획서가 전제하는 확정 사항

### D1. ★ CSS는 `style.css` 한 파일만 고친다 — JSP를 열면 그게 실패 신호다

설계서 §9 Phase 6-1이 명시했다: **"`style.css` 한 파일만 채운다. JSP는 열지 않는다."**

이건 스타일 작업 지침이 아니라 **아키텍처 검증**이다. Phase 1부터 다섯 Phase 동안 "의미 기반 클래스 이름만 쓰고 CSS 규칙은 안 쓴다"를 지켜 왔고, 그 판단이 옳았는지는 지금 딱 한 번 확인된다.

**JSP를 열어야 한다면 §4.4.2의 명명 규칙이 지켜지지 않았다는 신호다.** 그때는 남은 화면을 손대지 말고, 스타일이 적용된 화면만 데모 대상으로 삼는다 — 설계서가 그렇게 적었다.

실측 근거가 이미 둘 있다:
- Phase 1의 최소 CSS 66개 규칙 — **JSP diff 0**
- Phase 2의 상태 배지 CSS — **JSP를 열지 않음**, 클래스 목록이 실제 사용과 정확히 일치

세 번째가 이번이고, 이번이 가장 크다.

**작업 순서를 고정한다:** ① 클래스 목록과 실제 사용을 대조 → ② 없는 이름·죽은 이름을 보고 → ③ `style.css` 만 편집 → ④ `git diff --stat` 으로 **JSP 변경 0줄** 확인.

### D2. ★★ 컨테이너 JVM 문자셋 — 로드맵이 Phase 0부터 경고한 항목

로드맵 §2의 "계획서 6의 필수 항목 ①" 이다. 그대로 옮긴다:

> `pom.xml` 은 Maven·테스트 포크·`spring-boot:run` **세 JVM 만** UTF-8 로 고정할 수 있다. **Phase 6의 외부 Tomcat 컨테이너 JVM 은 `catalina.sh` 가 띄우므로 pom 의 영향권 밖이다.** slim Linux 이미지는 `LANG` 이 `POSIX`/`C` 인 경우가 많고, JDK 17 은 UTF-8 기본값(JEP 400)이 없어 `file.encoding` 이 UTF-8 이 되지 않는다.

**증상이 고약하다: 로컬은 정상인데 컨테이너에서만 한글이 깨진다.** 로컬 `mvnw spring-boot:run` 으로는 절대 발견되지 않는다.

**조치:** `docker-compose.yml` 의 tomcat 서비스에 `JAVA_OPTS: -Dfile.encoding=UTF-8` 을 넣는다(또는 컨테이너 로케일을 UTF-8 로).

**검증은 컨테이너 안에서 한다.** 로컬에서 한글이 나오는 것은 증거가 아니다. 컨테이너로 띄운 화면을 HTTP 로 가져와 바이트를 UTF-8 로 디코딩해 한글을 확인한다.

### D3. DB 자격증명을 환경변수로 재정의 가능하게 한다

로드맵 "필수 항목 ③". `application.yml` 에 `flowmate/flowmate` 가 리터럴로 커밋돼 있다. 로컬 개발 컨테이너의 기본값이고 같은 값이 `docker-compose.yml` 에도 있어야 하므로 **지금까지는 문제가 아니었다.**

public 전환 시점에는 `${DB_PASSWORD:flowmate}` 형태로 바꾼다 — 커밋된 기본값은 그대로 동작하게 두면서 재정의 지점을 남긴다. **설정 한 줄이고 별도 도구는 쓰지 않는다.**

이건 "비밀을 숨기는 것"이 아니다. 데모 DB 비밀번호는 비밀이 아니다. **읽는 사람에게 "이 값은 바꿀 수 있는 자리"라고 알려주는 것**이 목적이다.

### D4. ★★ 비밀값 재검은 작업 트리가 아니라 **이력 전체**를 본다

로드맵 "필수 항목 ②". **한 번 push 된 비밀값은 커밋을 되돌려도 원격 이력에 남는다 — 전환 전이 마지막 기회다.**

`.gitignore` 가 1차 방어선이고 이 재검이 2차다. 작업 트리만 보는 것은 재검이 아니다.

```powershell
git log --all -p -S "sk-ant" --oneline      # Anthropic 키
git log --all -p -S "AIza"  --oneline       # Google 키
git log --all -p -- src/main/resources/     # 설정 파일 이력 전체
git log --all --diff-filter=A --name-only | Select-String -Pattern '\.env|application-local|secret'
```

**전부 0건이어야 한다.** 한 건이라도 나오면 public 전환을 멈추고 먼저 그것을 처리한다.

Phase 5 종료 시점에 `AIza` 는 이미 0건으로 확인했지만, **그 뒤로 커밋이 더 쌓였으므로 전환 직전에 다시 본다.** "전에 봤으니 괜찮다"는 재검이 아니다.

### D5. `docker compose up` 한 번으로 뜬다 — 그리고 그것을 처음부터 확인한다

설계서 §9 Phase 6-2의 완료 기준이 "컨테이너에서 전체 기능이 동작한다"이다.

**★ 이 확인은 반드시 빈 볼륨에서 시작한다.** 지금 컨테이너에는 다섯 Phase 동안 쌓인 데이터가 있고, init 스크립트는 빈 볼륨에서만 돈다. 기존 볼륨으로 확인하면 **"새로 클론한 사람도 되는가"에 대한 답이 안 된다** — 그게 이 Task의 유일한 질문이다.

그러므로 **이 Phase에서 `docker compose down -v` 를 딱 한 번 쓴다.** 지금까지 금지해 온 명령이고, 여기가 그것이 정당한 유일한 지점이다:

- 지우는 데이터는 **전부 init 스크립트가 다시 만든다**(시드 6종 + 데모 200건)
- 손으로 만든 데이터는 각 Phase 검증 때마다 정리해 왔으므로 없다
- **"빈 상태에서 뜨는가"를 확인하는 것이 목적 그 자체다**

실행 전에 현재 행 수를 기록하고, 실행 후 같은 수가 나오는지 대조한다. 다르면 init 스크립트가 불완전하다는 뜻이고, 그건 **새 사용자에게 그대로 일어날 문제**다.

### D6. 남은 이월 항목을 닫거나 명시적으로 남긴다

로드맵 §2.0의 이월 항목 중 아직 열려 있는 것:

| # | 항목 | 이 Phase의 처리 |
|---|---|---|
| C1 | `LoginEmployee.eraseCredentials()` 와 캐시 | **문서로 남긴다.** 캐시를 붙이지 않는 한 안전하고, 붙일 이유가 없다. README 의 "알려진 제약"에 적는다 |
| C4 | `SecurityConfig` 의 `/WEB-INF/views/login.jsp` permitAll | **그대로 둔다.** Phase 2에서 실측으로 필요함을 확인했고 주석에 근거가 남아 있다. README 에 한 줄 적는다 |

**닫지 못하는 것을 조용히 지우지 않는다.** 포트폴리오에서 "남은 과제를 안다"는 것은 약점이 아니라 강점이다.

### D7. 기능 3b는 만들지 않는다

설계서 §9.1이 지정한 **잘라내기 1순위**이고, 설계서 자신이 "밀리면 포기" 항목으로 적었다.

지금 시점에 굳이 넣으면 CSS 마감(0.5일)을 잠식한다. 설계서가 그 트레이드오프를 이미 계산해 뒀다 — 그 판단을 뒤집을 새로운 근거가 없다.

**README 에 "설계서가 잘라내기 1순위로 지정했고 계획대로 잘라냈다"고 적는다.** 못 한 것이 아니라 결정한 것이다.

## Task 1: 클래스 목록과 실제 사용 대조

CSS를 쓰기 **전에** 한다. 대조 없이 쓰면 없는 이름에 스타일을 주거나 실제 이름을 빠뜨린다.

```powershell
# JSP 가 실제로 쓰는 클래스 (EL 이 섞인 것은 손으로 계열 처리)
Select-String -Path src/main/webapp/WEB-INF/views/**/*.jsp -Pattern 'class="([^"]+)"' -AllMatches
```

양방향을 본다:

- **JSP에 있는데 목록에 없다** → 마감에서 빠뜨릴 이름
- **목록에 있는데 아무도 안 쓴다** → 죽은 CSS를 쓰게 될 이름

★ **시각 기반 이름(`.blue-*`, `.big-*`, `.red`, `.mt-10`)이 하나라도 있으면 보고한다.** 있으면 명명 규칙이 무너진 것이고, 그건 D1이 검증하려는 바로 그 지점이다. **이름을 고치지 않는다** — 고치려면 JSP를 열어야 하고, 그 순간 이 Phase의 검증이 무의미해진다.

## Task 2: ★ CSS 마감 — `style.css` 한 파일

설계서가 준 범위: 폰트·여백·테이블 줄무늬·버튼·상태 배지 정도로 **"창피하지 않은 최소선"**. 화려할 필요가 없다.

- 색은 적게 쓴다. 상태 배지 6종은 이미 Phase 2에서 색이 정해져 있다
- 레이아웃(사이드바 + 콘텐츠)은 이미 골격이 있다
- **반응형은 하지 않는다** — 데스크톱 그룹웨어이고 설계서 범위 밖이다

**완료 조건: `git diff --stat` 에 `style.css` 외의 파일이 없다.**

## Task 3: 컨테이너 문자셋과 전체 기동 (D2 · D5)

1. `docker-compose.yml` 의 tomcat 서비스에 `JAVA_OPTS: -Dfile.encoding=UTF-8`
2. `mvnw clean package` → WAR
3. **현재 행 수를 기록**
4. **`docker compose down -v`** (이 Phase의 유일한 사용 — D5)
5. `docker compose up -d`
6. init 스크립트 로그에서 6개 SQL 파일이 전부 돌았는지, ERROR 가 없는지 확인
7. 행 수를 3번과 대조
8. **컨테이너 안의 JVM 문자셋을 직접 확인**
9. 브라우저 흐름 확인 — 로그인 → 기안 → 상신 → 승인 → 근태, **한글이 안 깨지는지**

★ 8·9번을 로컬 `spring-boot:run` 으로 대신하지 않는다. 그러면 D2가 경고한 바로 그 함정에 빠진다.

## Task 6: ★★ 비밀값 재검 (D4)

전환 **직전에** 한다. 앞 Task 들이 커밋을 더 만들기 때문이다.

D4의 네 명령을 전부 실행하고 **결과를 그대로 기록한다.** 한 건이라도 나오면 여기서 멈춘다.

## Task 7: public 전환 — **사용자가 직접 한다**

**내가 하지 않는다.** 되돌릴 수 없는 작업이고, 그 시점에 노출되는 것은 사용자의 저장소다.

Task 6의 재검 결과를 보여드리고, 사용자가 GitHub 화면에서 직접 전환한다:

> Settings → General → 맨 아래 Danger Zone → Change repository visibility → Make public

전환 후 `v1.0.0` 태그를 붙인다.
