# AI 사전점검 평가셋 실행 기록

설계서 §6.4.6 "★ 고정 평가셋 5건"과 계획서 5(`2026-08-09-phase-5-ai-features.md`) Task 9 · D1의
산출물이다. "AI 기능 품질을 어떻게 검증했나"에 대한 답을 저장소 안에 남기기 위한 기록이므로,
프롬프트(`src/main/resources/prompts/preflight.v1.txt`)를 고칠 때마다 이 문서도 다시 채운다.

이 평가셋은 실제 Gemini API를 호출한다. 그래서 `PreflightEvalSetIT`(`src/test/java/com/flowmate/ai/eval/`)에
`@Tag("llm")`을 붙이고, `pom.xml`의 Failsafe 설정에서 기본값으로 제외한다 — API 키 없이
`mvnw clean verify`가 통과해야 한다는 계약(Phase 3 D3)을 이 평가셋 때문에 깨지 않기 위해서다.

### 모델 선정 — 수동 프로브로 확인한 것

- `gemini-2.0-flash`(`application.yml`의 예전 기본값)는 **폐지**됐다. 호출하면 404 또는 429가
  나는데, 429는 "쿼터 초과"처럼 보이지만 실제로는 폐지된 모델이라는 뜻이라 오해하기 쉽다.
- `gemini-2.5-*` 계열은 **신규 사용자에게 닫혀** 있다(404: "no longer available to new users").
- **`gemini-3.5-flash-lite`**가 현재 신규 API 키로 실제 동작하는 모델이다. `application.yml`과
  `AiProperties`의 기본값을 이 모델로 바꿨다(이전 기본값은 `gemini-2.0-flash`).
- 무료 등급 쿼터는 **모델별·일별**로 매겨진다. 폐지되거나 닫힌 모델을 무료 등급으로 호출하면
  진짜 쿼터 초과와 구분하기 어려운 429/404가 난다 — "왜 안 되지"의 첫 번째 용의자는 항상
  "그 모델이 아직 살아 있는가"다.

## 다섯 사례 결과 (2026-08-10 최종 실행)

설계서 §6.4.6 표 그대로: 1~3번은 문제 있는 문서 → `WARN` 기대, 4·5번은 잘 작성된 문서 →
`PASS`(또는 findings 빈 배열) 기대. **4·5번이 가장 중요하다** — 억지 지적을 잡아내는 유일한
장치이고, 이 기능이 "훈계하는 AI"가 아니라는 근거다. 그래서 4·5번에는 1~3번과 **같은 반려
신호**(과거 반려 이력)를 일부러 심어 두고, 그런데도 지적하지 않는지를 확인했다 — 신호를 아예
안 주면 findings가 빈 것이 "지적할 근거가 없어서"인지 "애초에 볼 게 없어서"인지 구분할 수 없다.

| # | 입력 | 기대 | 실제 verdict | category | basedOnRejectCount | 결과 |
|---|---|---|---|---|---|---|
| 1 | 목적이 "업무협의"뿐인 출장비 | WARN(목적불명확, HIGH) | WARN | INSUFFICIENT_CONTENT | 6 | **통과** |
| 2 | 첨부 없는 출장비 정산 | WARN(증빙누락) | WARN | MISSING_EVIDENCE | 5 | **통과** |
| 3 | 부서 평균 4배 금액의 구매 | WARN(금액과다) | WARN | EXCESSIVE_AMOUNT | 7 | **통과** |
| 4 | 잘 작성된 출장비 | PASS | PASS | — | — | **통과** |
| 5 | 잘 작성된 구매 요청 | PASS | PASS | — | — | **통과** |

### 사례 1 — 목적 불명확 (WARN, HIGH)

```json
{
  "severity": "HIGH",
  "category": "INSUFFICIENT_CONTENT",
  "message": "출장 목적이 '업무협의'로만 기재되어 있어 구체적인 대상이나 안건 등 세부 내용이 누락되었습니다.",
  "suggestion": "'업무협의' 대신 협의 대상 기관명이나 구체적인 안건명을 포함하여 목적을 명시해 주십시오.",
  "basedOnRejectCount": 6
}
```

입력 문서는 교통비·숙박비·식비 내역과 영수증 첨부까지 상세히 적혀 있지만 출장 목적란만
"업무협의"로 뭉뚱그려 적었다. 세부 항목이 충실해도 핵심 목적이 불명확하면 지적한다는 것을
실제로 확인했다 — 아래 "프롬프트 반복" 절의 1차 수정이 겨냥한 지점이다.

### 사례 2 — 증빙 누락 (WARN)

```json
{
  "severity": "HIGH",
  "category": "MISSING_EVIDENCE",
  "message": "본문에 영수증을 분실하여 첨부하지 못했다고 기재되어 있으나, 증빙 자료가 누락되었습니다.",
  "suggestion": "지출 증빙을 위한 대체 영수증 또는 관련 확인서를 발급받아 첨부하시기 바랍니다.",
  "basedOnRejectCount": 5
}
```

출장 목적은 구체적으로 적었지만(부산 지사 물류관리 시스템 도입 협의) "영수증을 분실하여
첨부하지 못했습니다"라고 명시한 문서다. 목적이 명확한데도 증빙 누락만 정확히 짚었다 — 신호가
여러 개일 때 해당하는 것만 골라 지적한다는 근거다.

### 사례 3 — 금액 과다 (WARN)

```json
{
  "severity": "HIGH",
  "category": "EXCESSIVE_AMOUNT",
  "message": "총 구매 금액이 24,000,000원으로 최근 6개월간 평균 구매 금액인 6,000,000원을 크게 초과하며, 비고란에 '별도 사유 설명 없이 일괄 구매를 요청합니다'라고 기재되어 있어 금액 과다에 대한 구체적인 산출 근거가 부족합니다.",
  "suggestion": "노트북 20대 일괄 구매가 필요한 구체적인 산출 근거와 예산 적정성 소명 자료를 본문에 보완하여 재상신하시기 바랍니다.",
  "basedOnRejectCount": 7
}
```

문서에 적힌 "부서 평균 6,000,000원 대비 24,000,000원(약 4배)"이라는 참고 수치를 정확히
인용하고, 근거 부족(별도 사유 설명 없음)까지 짚었다.

### 사례 4·5 — 잘 작성된 문서 (PASS, findings 없음) ★

```
verdict=PASS
findings=[] (지적 없음)
```

두 사례 모두 `ai_preflight_result`에 기록되지 않았다(PASS는 저장하지 않는 설계 — `PreflightRecord`
클래스 주석 참고). 사례 4는 사례 1·2와 같은 반려 신호(INSUFFICIENT_CONTENT 6건 + MISSING_EVIDENCE
4건)를, 사례 5는 사례 3과 같은 신호(EXCESSIVE_AMOUNT 7건)를 문서에 심어 둔 상태에서도 지적하지
않았다 — 신호가 있어도 실제 문서 내용이 그 신호에 해당하지 않으면 findings를 만들어내지
않는다는 것을 확인했다.

## 프롬프트 반복 — 실패, 원인, 수정, 재확인

**3회의 프롬프트 수정을 거쳐 5/5에 도달했다.** 처음부터 통과한 것이 아니라는 사실 자체를
기록으로 남긴다 — 통과시키려고 기대치를 낮춘 적은 없다.

### 1차 실행 — 사례 1 실패(거짓 PASS)

첫 실행에서 사례 1(목적 불명확)이 **PASS**로 나왔다. 세부 항목(금액·일정·증빙)이 충실하게
적혀 있어서, 모델이 "문서 내용 불충분" 신호를 "출장 목적이 뭉뚱그려져 있다"는 구체적 문제와
연결하지 못한 것으로 보였다. `preflight.v1.txt`에 다음 규칙을 추가했다:

> "[과거 반려 패턴]에 '문서 내용 불충분' 유형이 있다면, 금액·일정 등 세부 항목이 잘 정리되어
> 있어도 신청 목적·사유 자체가 '업무협의', '업무 처리'처럼 구체적인 대상(기관명·거래처·안건)이나
> 산출물 없이 뭉뚱그려 적혀 있는지 반드시 함께 확인한다. 목적이 그렇게 적혀 있다면 다른 항목이
> 아무리 상세해도 그 자체가 '문서 내용 불충분'에 해당한다."

같은 김에 응답 형식을 강제하는 방어적 규칙도 추가했다("JSON 객체 하나만 출력한다 - 코드
블록이나 설명 문장을 앞뒤에 붙이지 않는다"). 이 규칙은 이번 실패의 직접 원인은 아니었지만
구조화 출력의 일반적인 실패 모드(마크다운 코드펜스 혼입)에 대한 선제 방어다.

### 재실행 — 사례 1이 간헐적으로 다시 실패(JSON 파싱 실패)

수정 후에도 사례 1이 **3번 중 2번** `Optional.empty()`로 떨어졌다(`ai_call_log`는 `success_yn=Y`,
즉 API 호출 자체는 성공). `PreflightService.parseSafely()`가 파싱 실패를 조용히 삼키므로
(설계상 의도된 폴백 — D8), 원인을 보려면 게이트웨이를 직접 호출하는 임시 진단 테스트를 만들어
같은 프롬프트로 4번 반복 호출했다. 그 중 3번에서 원문이 이렇게 나왔다:

```json
{ "basedOnRejectCount": "6건", ... }
```

`Finding.basedOnRejectCount`는 Java `int` 필드인데, 모델이 [과거 반려 패턴]에 적힌 "6건"이라는
표기를 프롬프트 지시("건수를 그대로 옮겨 적는다")를 문자 그대로 해석해 단위(건)까지 통째로
따옴표 붙은 문자열로 복사한 것이다. Jackson이 `"6건"`을 `int`로 변환하지 못해 매번
`JsonProcessingException`이 났다. `preflight.v1.txt`에 다음을 추가했다:

> "★ basedOnRejectCount는 JSON 숫자(정수)다. [과거 반려 패턴]에는 '6건'처럼 단위가 붙어 있지만
> 그 단위(건)는 옮기지 않는다 - '6'이 아니라 6으로, 따옴표 없는 숫자로 쓴다."

### 최종 확인

수정 후 전체 5건을 다시 실행해 **5/5 통과**했고(위 표), 사례 1만 별도로 한 번 더 실행해
`basedOnRejectCount`가 다시 정수로 나오는 것을 확인했다(2/2 연속 정상).

### 부수적으로 발견한 테스트 버그(프롬프트 문제 아님)

같은 조사 과정에서 사례 2의 `category`가 `"증빙 누락"`(한글 라벨)으로 나온 적이 있었다. 처음엔
`RejectReason.MISSING_EVIDENCE`(영문 코드) 문자열과 정확히 같아야 통과하도록 단정해서 실패로
잡혔는데, **설계서 §6.4.6의 출력 스키마 예시 자체가 category를 코드가 아니라 자유 텍스트
("목적불명확")로 보여준다** — 이 필드가 반드시 상수 문자열 그대로 나온다는 보장은 스키마
어디에도 없었다. "증빙 누락"은 `RejectReason.labelOf(MISSING_EVIDENCE)`와 정확히 같은 한글
라벨이라 의미상 완전히 맞는 답이었다. 프롬프트가 아니라 **평가셋의 단정이 과도하게 엄격했던
것**이라 판단해, 코드 문자열과 한글 라벨 둘 다 인정하도록 테스트를 고쳤다(`matchesCategory`
헬퍼, `PreflightEvalSetIT.java`). "실제 문자열이 아니라 실질을 본다"는 이 평가셋의 원칙에
맞춘 수정이다.

## 토큰 사용량과 대략적인 비용 (최종 5/5 실행)

| # | input_tokens | output_tokens | latency_ms |
|---|---:|---:|---:|
| 1 | 1,014 | 131 | 933 |
| 2 | 1,042 | 122 | 994 |
| 3 | 1,002 | 192 | 1,350 |
| 4 | 1,082 | 18 | 630 |
| 5 | 1,047 | 18 | 1,415 |
| **합계** | **5,187** | **481** | — |

이 실행은 **무료 등급**(결제 계정 미연결)으로 돌았으므로 **실제 청구 비용은 0원**이다. 유료
등급으로 환산했을 때의 대략적인 규모를 가늠하기 위한 참고치로, Gemini Flash-Lite급 모델의
공개된 유료 단가는 대체로 백만 입력 토큰당 낮은 십원 단위, 백만 출력 토큰당 그보다 높은
자리수 — 이 5건 전체(입력 5,187 + 출력 481 토큰)를 유료로 환산해도 실질적으로 **1원 미만**
수준이다. 이 프로젝트 시점 기준 정확한 단가를 검증하지 않았으므로 정확한 금액이 아니라
"무시할 수 있는 수준"이라는 규모 감각으로만 참고한다.

PASS로 끝난 4·5번의 출력 토큰이 18로 유독 작은 이유: `{"verdict":"PASS","findings":[]}` 자체가
아주 짧은 JSON이라서다 — WARN 응답은 finding마다 message·suggestion 문장이 붙어 100~200
토큰대로 늘어난다.

## 무료 등급이 의미하는 것 — 알아 둘 것

- **쿼터는 모델별·일별이다.** 폐지되거나 닫힌 모델(`gemini-2.0-flash`, `gemini-2.5-*`)을
  무료 키로 부르면 진짜 "오늘 쿼터를 다 썼다"는 429와 구분하기 어려운 429/404가 난다 — 이
  Phase에서 실제로 겪은 함정이다(위 "모델 선정" 절 참고). 429/404가 뜨면 먼저 그 모델이
  아직 서비스 중인지부터 확인한다.
- **무료 등급과 유료 등급은 데이터 사용 방침이 보통 다르다.** 일반적으로 무료 등급은 제출된
  데이터를 서비스 개선(모델 학습 등)에 쓸 수 있다고 명시하는 경우가 많고, 유료(결제 연결)
  등급은 그렇지 않다고 명시하는 경우가 많다 — 정확한 현재 약관은 공급자 문서에서 직접
  확인해야 하는 항목이라 이 문서는 "그런 구분이 존재한다"는 사실만 기록한다. 그래서 이
  프로젝트는:
  - **개인정보를 API 호출 전에 마스킹한다** — `MaskingLlmClient`/`SensitiveDataMasker`가
    주민등록번호·계좌번호·전화번호·사업자등록번호·카드번호·이메일을 실제 값이 밖으로 나가기
    전에 치환한다(설계서 §6.4.1, Phase 3).
  - **사전점검은 반려 사유 원문을 절대 보내지 않는다** — `RejectHistoryMapper.findRecentReasonCategories`가
    SELECT 목록에 `reason_text`를 아예 넣지 않는다(사람 이름과 금액이 들어 있는 자유 텍스트).
    프롬프트에는 `reason_category`(유형)와 건수만 들어간다 — 이번 평가셋의 다섯 문서에도
    실제 사람 이름·연락처·계좌 정보는 전혀 쓰지 않았다.
  - **이 평가셋을 포함한 현재 모든 데이터는 데모 시드다.** 사원 20명, 부서 7개, 문서 6건(기본
    시드) + 200건(대량 데모 시드) 전부 가상의 인물·거래로 구성되어 있고, 실사용자 정보는
    이 저장소 어디에도 없다.

## 재실행 방법

```powershell
$env:JAVA_HOME = [Environment]::GetEnvironmentVariable('JAVA_HOME','User')
$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')
$env:GEMINI_API_KEY = [Environment]::GetEnvironmentVariable('GEMINI_API_KEY','User')

.\mvnw.cmd verify "-Dit.test=PreflightEvalSetIT" "-Dgroups=llm" `
    "-Dflowmate.eval.excludedGroups=" "-Dai.enabled=true"
```

`-Dgroups=llm`만으로는 부족하다 — `pom.xml`의 Failsafe `excludedGroups` 기본값이 이미 `llm`이라,
켜는 필터(`groups`)와 끄는 필터(`excludedGroups`)가 같은 태그를 가리키면 JUnit5의 태그 필터
결합 규칙상 끄는 쪽이 항상 이긴다. 그래서 `-Dflowmate.eval.excludedGroups=`(빈 값)으로
`excludedGroups`도 함께 비워야 실제로 실행된다(`pom.xml`의 `flowmate.eval.excludedGroups`
프로퍼티 주석, `PreflightEvalSetIT` 클래스 주석 참고).

기본 빌드(`mvnw clean verify`, 키 미설정)는 이 평가셋을 항상 건너뛴다 — `@Tag("llm")` +
Failsafe `excludedGroups` 기본값 `llm` 조합이 그 계약(Phase 3 D3, 계획서 5 D1)을 지킨다.
